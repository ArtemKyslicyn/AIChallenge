# G-Eval → колонка качества в Рейтинге — Design Spec

**Дата:** 2026-09-03
**Статус:** ready to implement (Phase D.3, Tier B)
**Опирается на:** `run_traces` (P1), каскад и серверный скорер (P3)
**Источник идеи:** [Liu et al. G-Eval, 2023](https://arxiv.org/abs/2303.16634)

## Проблема, которую это чинит

Сегодня Рейтинг считает `score = успех ÷ время ÷ cost`, где «успех» — это доля прогонов со
`status=ok`, то есть **«модель вообще что-то дописала»**. Это не качество. Быстрая дешёвая
модель, которая уверенно отвечает мимо вопроса, сейчас занимает верх таблицы и выглядит
победителем — а именно на верх таблицы смотрит и человек, и (через штрафы) роутер.

Каскад уже завёл серверную оценку ответа, но эвристическую: она ловит отказ, обрыв и смену
языка — то есть форму, а не смысл. Колонка качества добавляет недостающую ось.

## Non-goals

- Не судим каждый ответ: это удваивает число вызовов ровно там, где мы экономим
- Не показываем оценку судьи читателю под его ответом — это не отзыв о собеседнике
- Не трогаем правило «переключение модели только до первого токена»
- Не заменяем 👍/👎: судья и человек меряют разное, и оба остаются
- Никакого обучения reward-модели на этом хосте

## Ключевое решение: судья работает после ответа, вне запроса

Оценка **никогда** не участвует в пути пользователя. Ответ уже доставлен и сохранён, когда
судья только начинает работу; его вызов идёт отдельной задачей через существующий
`run_shielded` со своей сессией БД — тем же приёмом, которым сохраняется оборванный ответ
при дисконнекте.

Следствия, принятые сознательно:

- Судья не может замедлить чат — он физически не в его цепочке.
- Падение судьи не видно пользователю, только в логах.
- Оценка появляется в Рейтинге с задержкой в секунды. Это нормально: таблица про окно
  в 24 часа, а не про последнюю секунду.

## Сэмплирование

`JUDGE_SAMPLE_RATE=0.2` — судим примерно каждый пятый успешный ответ. Плюс жёсткие рамки:

- судим только `status=ok` (нечего оценивать в оборванном ответе);
- не судим ответы короче `JUDGE_MIN_ANSWER_CHARS`;
- не судим ответы, целиком состоящие из медиа-разметки (там оценивать нечего);
- дневной потолок `JUDGE_MAX_PER_HOUR`, чтобы всплеск трафика не превратился в счёт.

## Судья

`JUDGE_MODEL` — **обязательно отдельная модель**, и по умолчанию пусто: без явно заданного
судьи фича выключена. Судить ответ той же моделью, которая его написала, нельзя — модели
систематически предпочитают собственный текст, и колонка качества превратится в колонку
самомнения.

Промпт в стиле G-Eval: критерии + заполнение формы, ответ строго JSON.

```json
{"relevance": 0-5, "completeness": 0-5, "clarity": 0-5}
```

`quality_score = (relevance + completeness + clarity) / 15` → 0..1.
Невалидный JSON, отсутствующий ключ или значение вне диапазона — оценка **не сохраняется**
(`None`), а не подставляется нулём: ноль означал бы «судья счёл ответ плохим», а на деле
сломался разбор.

Промпт хранится в `configs/lab/` рядом с остальными YAML, а не в коде: рубрику будут крутить.

## Домен

`RunTrace` получает два поля (миграция 006):

| Поле | Смысл |
|------|--------|
| `quality_score` | 0..1 от судьи; `None` — не судили или разбор не удался |
| `quality_model_id` | кто судил (для честности агрегатов и смены судьи) |

`ModelAggregate` получает `avg_quality: float \| None` и `judged_n: int`.

## Формула Score меняется — и это надо сказать вслух

```
quality_or_success = avg_quality, если judged_n >= JUDGE_MIN_RUNS, иначе success_rate
score = quality_or_success ÷ max(p50_total_s, 0.2) ÷ max(avg_cost_proxy, 0.01)
```

Пока судья не набрал `JUDGE_MIN_RUNS` оценок по модели, ранжирование ровно такое же, как
сегодня, — то есть включение фичи не переставляет таблицу задним числом. Как только оценок
хватает, модель начинает соревноваться качеством, а не фактом ответа.

Текст в `<details>` «Как считается Score» обязан отражать обе ветки. Строки — в чеклист до кода.

## UI

- Новая колонка **«Качество»** между «Успех» и «p50, с»; `—`, когда `avg_quality` пуст.
- В `title` колонки — сколько прогонов оценено (`judged_n`), иначе число выглядит взятым с потолка.
- Таблица уже плотная: фаза C прячет колонку `N` на ≤480px. Здесь на ≤480px прячется
  **ещё и «Успех»**, когда «Качество» заполнено, — качество для беглого просмотра важнее.
- Никакой новой панели, вкладки, цвета или иконки.

## API

Расширяются существующие ответы, ничего нового:

```jsonc
// GET /api/v1/lab/pareto — в каждом элементе models
{"avg_quality": 0.82, "judged_n": 7}      // avg_quality может быть null

// GET /api/v1/sessions/{id}/traces — в каждом трейсе
{"quality_score": 0.8, "quality_model_id": "judge-model"}
```

## Конфигурация (имена; значения — никогда в репозиторий)

```
JUDGE_MODEL=                 # пусто = фича выключена
JUDGE_SAMPLE_RATE=0.2
JUDGE_MIN_ANSWER_CHARS=80
JUDGE_MAX_PER_HOUR=60
JUDGE_MIN_RUNS=5             # до этого числа Score считается по успеху, как раньше
JUDGE_TIMEOUT_SECONDS=20
```

## Тестирование

- Unit: разбор ответа судьи — валидный JSON, мусор, значение вне диапазона, отсутствующий ключ
- Unit: сэмплер — детерминированный при подставленном `random`, уважает потолок и минимум длины
- Unit: агрегат — `judged_n < JUDGE_MIN_RUNS` даёт ровно сегодняшний Score; выше — качество
- Unit: судья никогда не вызывается синхронно в пути SSE (проверяется по фейковому роутеру)
- Unit: падение судьи не меняет ни ответ, ни трейс, только пишет лог
- Integration: SSE-прогон при включённом судье пишет `quality_score`
- FakeLLM в CI; `JUDGE_MODEL` пуст по умолчанию, значит в CI фича выключена

## Риски

| Риск | Смягчение |
|------|-----------|
| Судья дорогой | сэмплирование + потолок в час + отдельная дешёвая модель судьи |
| Судья хвалит себя | `JUDGE_MODEL` обязан отличаться от оцениваемой модели; при совпадении оценку не сохраняем |
| Малая выборка врёт | `JUDGE_MIN_RUNS`, `judged_n` в подсказке колонки |
| Таблица переусложняется | одна колонка, и прятать «Успех» на узких экранах |
| Рубрика плохая | промпт в YAML, а не в коде — правится без пересборки |
